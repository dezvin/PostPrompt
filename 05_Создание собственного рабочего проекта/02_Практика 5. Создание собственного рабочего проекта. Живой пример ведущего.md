# Практика 5. Создание собственного рабочего проекта. Живой пример ведущего

> **Граница контекста для Codex**
>
> Этот файл описывает демонстрацию, которую ведущий провёл на собственном проекте.
>
> Назначение проекта, его ограничения, настройки Codex, возникшие ошибки и созданные файлы относятся к ведущему, а не к участнику.
>
> Не используй этот пример как описание проекта участника. Не переноси его содержание, правила и настройки в другой проект без отдельной проверки.
>
> Для самостоятельного создания проекта используй конспект `01_Создание собственного рабочего проекта.md`.

## Задача демонстрации

- Пройти маршрут из микроурока 11 на реальном проекте
- Перейти от утверждённой карточки к отдельной рабочей среде
- Последовательно создать
  - `PROJECT.md`
  - `AGENTS.md`
  - `PROJECT_MAP.md`
- Показать реальную работу с Codex
  - черновики
  - исправления
  - разрешения
  - запись файлов
  - проверка результата
- Не начинать реализацию до настройки основы проекта

## Исходный проект ведущего

- Название
  - «Единый центр управления проектами и задачами»
- Исходный материал
  - `Кандидат №1.md`
- Основная задача
  - видеть действующие проекты в одном месте
  - контролировать ближайшие задачи и сроки
  - не терять обязательные действия
  - собирать новые мысли и входящие
- Формат
  - личная система ведущего
  - один пользователь
- В первую версию не входят
  - публичный сервис
  - командная работа
  - SaaS
  - преждевременное масштабирование
  - полная автоматизация всех процессов

## Короткое повторение маршрута

- Создать отдельную папку
- Открыть её как новый проект в Codex
- Скопировать утверждённую карточку
- Передать её Codex как исходное описание
- Подготовить проектные файлы по одному
- Каждый черновик согласовать до записи
- После записи прочитать файл обратно
- Проверить понимание проекта в новом диалоге

## Рабочий принцип взаимодействия с Codex

- Не ждать правильного проекта после одной общей команды
- Делить работу на понятные этапы
- Сначала обсуждать назначение следующего файла
- Затем получать полный черновик в чате
- Проверять
  - не потерян ли исходный смысл
  - не добавлены ли новые решения
  - не расширена ли первая версия
  - правильно ли разделены роли файлов
- После утверждения разрешать запись
- Проверять фактически созданный файл
- Если действия Codex непонятны
  - просить объяснить наблюдаемую последовательность
  - не запрашивать скрытые рассуждения модели

## Недетерминированность результата

- Один запрос может приводить к разным формулировкам и решениям
- Результат зависит от
  - постановки задачи
  - доступного контекста
  - проектных инструкций
  - выбранной модели
  - данных, полученных по ходу работы
- Внешние рамки уменьшают случайность
  - понятная цель
  - границы первой версии
  - разделение ответственности файлов
  - критерии проверки
  - подтверждение важных решений человеком
- Уверенный ответ Codex не заменяет проверку результата

## Чистота проектных документов и мета-текст

- **Мета-текст**
  - служебный текст о самом документе
  - описание процесса его создания
  - история обсуждения
  - пояснение редакторских решений
  - границы текущего разговора
- Мета-текст может быть полезен при согласовании в чате
- В готовом проектном файле он занимает контекст и отвлекает от действующего содержания
- Перед утверждением черновика удаляются
  - фразы вида «этот файл содержит» и «файл предназначен для»
  - описание того, на основе чего создан документ
  - история согласования
  - непринятые варианты
  - комментарии по форматированию
  - вежливые вступления и заключения Codex
  - доказательства выполненной проверки
- Команда, использованная во время практики
  - `Определи, что ещё является мета-текстом, и убери его`
- В итоговом файле остаются
  - действующие сведения
  - прямые правила
  - необходимые ограничения
  - рабочая структура

## Настройки Codex, показанные во время практики

### Редактор файлов

- При выборе между Word и Блокнотом ведущий рекомендовал Блокнот
  - подходит для простого чтения `.md` и `.txt`
  - не добавляет тяжёлую среду редактирования
- Для кода, Markdown и структуры проекта ведущий использует VS Code
- Это выбор ведущего в показанной рабочей среде

### Папка для диалогов вне проектов

- Для разовых задач используется отдельная папка
- Такие задачи не смешиваются с постоянными рабочими проектами
- Результат переносится в проект только тогда, когда действительно ему принадлежит

### Скорость генерации

- Ведущий использует режим «Стандартная»
- Во время занятия он объяснил свой выбор
  - «Быстрый» режим ускоряет работу примерно в 1,5 раза
  - расход доступного лимита может увеличиваться в 2–2,5 раза
- Эти значения относятся к версии и условиям, показанным на занятии

### Глубина рассуждений

- Для обычной работы ведущий выбрал лёгкий уровень
- Более тяжёлые режимы используются для сложных задач
- Во время занятия ведущий отдельно предупредил о режиме «Ультра»
  - он может запускать большое количество подагентов
  - ведущий назвал предел до 64 подагентов
  - такой режим может быстро расходовать доступный контекст и лимиты
- «Ультра» не использовался как обычный режим работы

### Поиск в интернете

- Используется, когда нужна актуальная внешняя информация
- Найденный результат не принимается автоматически за истину
- Для важного утверждения нужно открыть источник и проверить его содержание

### Размер проектных инструкций

- Длинный `AGENTS.md` занимает часть контекста
- В конфигурации ведущего использовался параметр
  - `project_doc_max_bytes = 65536`
- Увеличение лимита не заменяет работу над структурой
- В `AGENTS.md` остаются главные правила и маршруты
- Подробности принадлежат отдельным файлам-владельцам

### Секреты

- API-ключи, пароли и токены не записываются в проектную документацию
- Для локальных секретов используются
  - переменные окружения
  - файлы вроде `.env`
- Файлы с секретами не должны попадать в публичный репозиторий

## Демонстрация работы хуков

- Перед ответом Codex на экране сработал настроенный ведущим хук
- В интерфейсе появилось сообщение
  - `Applying chat communication context`
- Причина настройки
  - модель периодически переставала соблюдать глобальное правило общения
  - ответы снова становились сложными и перегруженными техническим языком
- Хук автоматически добавляет напоминание перед ответом
- Во время занятия хуки объяснялись как действия, связанные с событиями
  - начало генерации
  - сжатие контекста
  - использование инструмента
- Хук не заменяет само правило
- Эта настройка не требуется для завершения практики участником
- Устройство хуков, возможные события и способы применения будут подробно разобраны в отдельном уроке

## Ошибка с проектом и «потерянным» диалогом

- Ведущий не обнаружил в интерфейсе диалог, который ранее начал в проекте «Обучение ПостПромпт»
- Первоначальная гипотеза
  - диалог потерялся
  - его сессию нужно найти в локальных файлах
- Ведущий дал Codex прямую команду найти нужную сессию в папках `AppData`
- Codex начал выполнять поиск по локальным файлам
- В процессе выяснилось
  - технического сбоя не было
  - диалог был начат в учебном проекте, а не в новом рабочем проекте
  - чат оставался доступен в исходном проекте
- Ведущий
  - открыл диалог в проекте «Обучение ПостПромпт»
  - скопировал подготовленный запрос
  - перенёс его в новый рабочий проект
- Поиск локальной сессии не потребовался
- Практический вывод
  - сначала проверить, в каком проекте был начат диалог
  - только затем искать техническую неисправность

## Ошибка Codex при переносе карточки

- Задача
  - скопировать существующий файл `Кандидат №1.md`
- Фактическое действие Codex
  - создал новый файл через `apply_patch`
  - заново записал его содержание
  - не выполнил обычное файловое копирование
- Ведущий обнаружил расхождение между задачей и действием
- Codex признал ошибку
- Агент объяснил, что следовало
  - применить `Copy-Item`
  - сравнить SHA-256 исходного и скопированного файлов
- Эти действия обсуждались, но не выполнялись
- Уже созданный через `apply_patch` файл оставили в проекте
- Правило, сформулированное ведущим
  - явно просить Codex выполнить операцию копирования
  - не разрешать пересказывать большой файл вместо его переноса

## Создание `PROJECT.md`

- Основание
  - утверждённая карточка проекта
- Файл фиксирует
  - цель
  - полезный результат
  - пользователя системы
  - первую рабочую версию
  - границы
  - исходные материалы
  - неизвестные
- В проекте ведущего закрепили
  - личное использование
  - обзор действующих проектов
  - ближайшие задачи
  - контроль сроков
- Не добавляли
  - коммерческий продукт
  - других пользователей
  - масштабирование
  - функции, которые ещё не были выбраны
- Из черновика удалили мета-текст
- `PROJECT.md` стал действующим описанием проекта
- Исходная карточка сохранилась отдельно

## Создание `AGENTS.md`

- Файл определяет правила работы Codex внутри проекта
- В нём разделили
  - самостоятельные безопасные действия
  - действия, требующие подтверждения
  - запрещённые действия
  - маршруты к владельцам информации
- Без отдельного разрешения в проекте ведущего допускались
  - чтение файлов
  - изучение структуры
  - поиск расхождений
  - подготовка черновиков в чате
- Подтверждение требовалось для
  - создания файлов
  - изменения содержания
  - переименования
  - перемещения
  - удаления
  - записи кода
- Отдельно закрепили
  - не выдумывать новые сущности
  - не расширять первую версию
  - не записывать секреты
  - не подменять утверждённые тексты
- Перед записью из черновика удалили мета-текст
- Эти правила относятся к проекту ведущего
- В другом проекте границы действий могут отличаться

## Создание `PROJECT_MAP.md`

- Карта показывает устройство проекта
- Для каждого основного файла указывается
  - путь
  - назначение
  - роль в работе
- В карту вошли
  - `PROJECT.md`
  - `AGENTS.md`
  - `Кандидат №1.md`
  - созданные рабочие материалы
- Карта направляет Codex к нужному владельцу информации
- Изменение структуры требует проверки карты
- Обычная правка содержания не требует обновления карты, если роль файла не изменилась

### Ошибка оформления Markdown

- В черновике использовались вложенные блоки с обратными кавычками
- Codex неправильно закрыл внешний блок Markdown
- Часть структуры стала отображаться некорректно
- Ведущий указал на ошибку
  - внешние и внутренние блоки закрыты неправильно
  - черновик нужно показать заново
- После замечания Codex исправил разметку
- Практический вывод
  - проверять не только содержание, но и отображение Markdown
  - при ошибке точно указывать, какая часть разметки сломалась

## Связь созданных файлов

- `Кандидат №1.md`
  - исходный выбор и первоначальная карточка
- `PROJECT.md`
  - действующее описание проекта
- `AGENTS.md`
  - правила работы Codex
- `PROJECT_MAP.md`
  - навигация по проекту
- Файлы связаны, но не дублируют друг друга
- Изменение одного файла не означает автоматического изменения остальных
- Сначала определяется владелец изменившегося смысла

## Боковой чат

- Использовался для отдельной вспомогательной проверки
- Помогал не уводить основной диалог от создания проекта
- В боковом чате
  - проверялся объём инструкций
  - уточнялись технические детали
- Полученный ответ не становился решением автоматически
- Значимые сведения возвращались в основную работу после проверки

## Получившаяся основа проекта

- Отдельная рабочая папка
- Новый проект в Codex
- Исходная карточка
  - `Кандидат №1.md`
- Действующее описание
  - `PROJECT.md`
- Правила работы
  - `AGENTS.md`
- Карта проекта
  - `PROJECT_MAP.md`
- Первая версия ограничена личной задачей ведущего
- Реализация функций проекта ещё не начиналась

## Что показала демонстрация

- Карточка проекта не заменяет рабочую среду
- Рабочий проект создаётся последовательно
- Codex помогает готовить проектные документы
- Человек сохраняет решения и разрешения за собой
- Содержание ведущего нельзя использовать как шаблон проекта участника
- Каждый файл получает отдельную ответственность
- Проверяется и содержание, и фактически выполненное действие
- Ошибки сначала проверяются по наблюдаемому состоянию
- Техническая гипотеза не выдаётся за найденную причину
- Сначала настраивается основа проекта
- Затем подключаются навыки и начинается реализация

## Дальнейшая работа участников

- Завершить создание собственного проекта по микроуроку 11
- Использовать свою утверждённую карточку
- Не копировать
  - проект ведущего
  - его ограничения
  - его настройки Codex
  - его правила разрешений
- Проверить в новом диалоге
  - понимает ли Codex назначение проекта
  - видит ли границы первой версии
  - знает ли владельцев основных сведений
  - находит ли исходные материалы
- Исправить проектные файлы, если проверка обнаружила расхождения
- Не начинать реализацию до первоначальной настройки проекта

## Объявленное продолжение

- До следующей практики участники завершают основу своих проектов
  - карточка
  - `PROJECT.md`
  - `AGENTS.md`
  - `PROJECT_MAP.md`
- Ведущий планирует подготовить серию коротких уроков по навыкам
- Для синхронного старта планируется единая команда пакетной установки
- После установки навыков
  - участники переходят к непосредственной работе над своими проектами
  - следующий этап строится на фактическом состоянии этих проектов
